0client.chat.completions.create(model=…, messages=…, tools=TOOLS)

一次 LLM 调用的剖面

从 create_completion() 里的一行 SDK 调用，到 GPU 上算出的下一个 token，再带着 tool_calls 绕回你的 agent——五层栈，一趟工具回环。

请求下行 响应与工具回环上行 断链风险（文末清单）
请求 ↓ ↑ 响应
1

调用方 — SDK 与你的 agent

openai SDK 只是讲普通话的 HTTP 客户端：把 Python 对象序列化成 JSON 报文 POST 出去，流式时读 SSE。call_llm.py 读环境变量、建 client，test_003.py 在这一层跑 agent 循环。

  • test_003.py 四步：上送工具清单 → 模型决策 → 执行工具 → 结果回传组织回答
  • call_llm.py：create_completion() 返回原始 completion（tool_calls 从这里取）；chat() 只取文本
  • 环境变量：LLM_API_BASE_URL_SIMPLE / LLM_API_KEY / LLM_MODEL 决定请求发往哪家的普通话服务
TOOLS = [{
  "type": "function",
  "function": {
    "name": "get_weather",
    "parameters": {
      "latitude":  {"type": "number"},   # 纬度，如杭州 30.25
      "longitude": {"type": "number"},   # 经度，如杭州 120.17
    }}}]                                 # test_003.py 的工具清单
2

API 协议 — 一份合同，不是软件

OpenAI 兼容格式是行业普通话：URL、字段、鉴权、响应结构的约定。这一层“支持 tools”只代表格式合法、照单转发，不代表模型会用。

字段作用谁校验
model路由到哪个模型（决定后面每一层长什么样）网关 / 引擎
messages对话历史，含 role=system / user / assistant / tool格式：网关；语义：模型
tools工具清单，供模型选择调用（本图主角）格式：网关；用不用：模型说了算
temperature采样随机度（test_002.py 的实验变量）引擎
streamtrue 时走 SSE 逐块回传网关 / 引擎
POST {base_url}/v1/chat/completions
Authorization: Bearer sk-***
Content-Type: application/json          # 换 base_url 即换厂商，普通话的威力
3

聚合网关 — one-api / new-api可选层 · 无 GPU · 无模型 · 纯转发

自己不跑任何模型，只做渠道管理、鉴权计费、负载均衡、故障转移。你买的“API 中转”背后多半是别人部署的 new-api。

one-api
 ├─ 渠道 1 · OpenAI 官方
 ├─ 渠道 2 · DeepSeek 官方
 ├─ 渠道 3 · 自建 vLLM 机器
 └─ 渠道 4 · 别人布的 new-api     # 链路可以套娃
  • 统一入口：几十个厂商/账号，下游只见一个 OpenAI 格式端点
  • 渠道管理：限速、挂了自动切下一个
  • 令牌与计费：不同用户不同 key，额度记账
4

推理引擎 — vLLM / SGLang

把模型权重高效跑在 GPU 上的开源引擎。模型不认识 JSON 字段——它读到的一切，都是引擎拼出来的扁平字符串；它吐出的一切，也是引擎解析回结构化字段的。

4achat template 渲染

Jinja2 模板把 messages + tools 渲染成模型真正读到的 prompt：

<|im_start|>system
You have access to
the following tools:
{"name":"get_weather",…}
<|im_end|>

4b调度与显存

continuous batching：请求随到随拼车；PagedAttention（vLLM）分页管 KV 缓存；RadixAttention（SGLang）复用公共前缀。

4c响应解析

识别模型输出的特殊格式，组装成 tool_calls 字段。少了它，API 照收 tools，响应里 tool_calls 恒为 null：

vllm serve Qwen… \
  --enable-auto-tool-choice \
  --tool-call-parser hermes
5

模型本体 — GPU 上的权重

Transformer 参数矩阵，唯一动作是预测下一个 token。它不会“调用函数”——只是生成约定格式的文本，能力完全来自训练。

训练阶段学到什么
预训练海量文本上猜下一个词 → 语言与世界知识
SFT指令→优质回答示范 → 听懂人话
RLHF人类偏好排序 → 有用、无害、稳定
工具调用微调工具定义→结构化调用示范 → function calling
# 模型吐的其实是这段文本，
# 引擎(4c)再把它解析成 tool_calls
<tool_call>
{"name": "get_weather",
 "arguments": {"latitude": 30.25,
               "longitude": 120.17}}
</tool_call>

tools 参数真正生效与否，由这一层说了算——协议接受 ≠ 模型会用。

6

工具回环 — 回到第 1 层，再下去一趟

  • ⑥ tool_calls 上行：引擎解析好的结构化调用随响应回到 agent：msg.tool_calls[0].function.name / .arguments（arguments 是 JSON 字符串，需 json.loads）
  • ⑦ agent 本地执行：get_weather(**args)——模型给的参数直接解包成函数实参 → 栈外真实 HTTP 请求 open-meteo
  • ⑧ 第二轮请求：assistant 消息（带 tool_calls 原样 append）+ role="tool" + tool_call_id 回传，再次穿过上面五层，模型组织自然语言回答
⑦ 栈外 · 外部世界
GET api.open-meteo.com/v1/forecast
?latitude=30.25&longitude=120.17
真正查到温度 22.4°C 的地方。模型从头到尾没碰过这里——动手的是你的 agent。

支持是一条链，断哪一环都不行

“这个服务支不支持 tools”不是一个问题是四个。最快的实证：跑一次 test_003.py，看 tool_calls 是否有值。

  • L2　网关不认识字段 → 直接报 400
  • L4a　chat template 没把工具渲染进 prompt → 模型根本不知道有工具
  • L4c　解析器没开（如 vLLM 缺 --tool-call-parser）→ tool_calls 恒为 null
  • L5　模型没训练过工具调用 → 无视 tools 文本作答，或在 content 里吐裸 JSON
