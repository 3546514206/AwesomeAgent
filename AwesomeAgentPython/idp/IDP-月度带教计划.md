## 一、总体目标与验收

四周结束时，学员应当能独立回答：**「模型只会输出文本，那 Agent 到底多做了什么？」**——并用
`idp/` 里的四个可运行程序回答：编排工具调用、跑决策循环、维护对话历史。

| 能力 | 起点 | 终点 | 对应产出 |
| --- | --- | --- | --- |
| 调用 LLM | 不会 | 封装统一入口、读懂 role 协议 | `idp/week1_chat.py` |
| 使用工具 | 不会 | 写得出 function calling 契约与分发 | `idp/week2_tool.py` |
| 自主决策 | 不会 | 跑通 ReAct 循环，知道何时停 | `idp/week3_react.py` |
| 多轮对话 | 每句都失忆 | 短期记忆 + 成本意识 | `idp/week4_memory.py` |

**总体验收**：四个脚本全部能由学员本人从终端输入驱动跑通，且能口述每一步「为什么这样写」。

## 第一周：跑通一个 LLM API 调用，实现单轮对话

### 目标
把「调模型」从玄学变成一条确定的链路：请求长什么样、响应长什么样、模型凭什么知道该回什么。

### 读这些代码
- `openai/call_llm.py:8-26` —— 唯一该被调用的地方。三个环境变量在 `:18-20` 读，
  `:22-23` 校验，`:26` 真正发请求。
- `openai/call_llm.py:29-31` —— `chat()` 只是把响应对象里的一行文本取出来。
- `openai/demo01.py:18-32` —— 把上面两层摊开手写一遍，看清 `messages` 的结构。
- `openai/demo02.py:18-31` —— `temperature` 从 0 到 2 的效果对比，理解「参数」是什么。

### 知识点
1. OpenAI 兼容协议：一次请求 = `model` + `messages` + 可选参数；一次响应 = `choices` + `usage`。
2. `role` 三件套：`system` 定角色与规则，`user` 是本轮输入，`assistant` 是模型自己的历史输出。
3. **模型没有记忆**：每次请求都是全新的，喂进去什么它才知道什么。
4. 采样参数 `temperature`：越低越确定，越高越发散。

### 动手任务
1. 跑 `openai/demo01.py`、`openai/demo02.py`，各说出一句观察。
2. 读 `openai/call_llm.py`，用一句话解释 `create_completion` 和 `chat` 的区别。
3. 写 `idp/week1_chat.py`：从终端读入问题，调 `common.create_completion`，打印回答。
   （`idp/common.py` 已经把 `create_completion` 复用过来了，不要重写客户端。）
4. 亲手验证「模型没记忆」：第一句说「我叫杨海波」，第二句问「我叫什么？」，观察它答不上来。

### 验收标准
- [ ] 独立跑通，不需要带教人贴命令
- [ ] 能指出三个环境变量各自的作用，缺哪个会报什么错
- [ ] 能解释为什么第二句它不记得第一句（用上面那个实验作证）
- [ ] 说得出 `system` 提示词改了会造成什么不同

### 常见坑
| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `SystemExit: 请先设置环境变量！` | 三个环境变量缺一 | `openai/call_llm.py:22-23` |
| 换模型后参数报错 | 兼容端点支持的参数不完全一致 | 先查该模型文档再传参 |
| 回答里出现 `<think>...</think>` | MiniMax-M3 会把思考过程放进 `content` | 展示前用正则剥离（延伸练习） |
| IDE 里报 `Unresolved reference` | 跨目录 import，IDE 索引不到 | `idp/` 内统一从同目录 import；要跨目录就把对方包成包 |

### 延伸练习
- 给 `week1_chat.py` 加一个「当前时间」工具（第二周用得上）。
- 用 `openai/tokenizer.py` 数一数这次对话花了多少 token。

## 第二周：学习 Tool 调用的方法，实现调用 Tool 输出结果

### 目标
理解 Agent 的本质：**模型不执行任何东西，它只输出「意图」，执行是程序干的活。**

### 读这些代码
- `openai/tool_use.py:10-24` —— 工具清单（JSON Schema）。这是模型的「说明书」。
- `openai/tool_use.py:30` —— 第一次调用，把 `tools` 传上去，模型可能回 `tool_calls`。
- `openai/tool_use.py:36-38` —— 模型选了什么工具、传了什么参数（参数是 **JSON 字符串**）。
- `openai/tool_use.py:41` —— **程序**执行工具，拿到真实数据。
- `openai/tool_use.py:44-50` —— 把 assistant 的 tool_calls 消息和 tool 结果一起塞回 `messages`，
  第二次调用，模型才把数据组织成自然语言。
- `openai/weather.py:4-33` —— 工具的真实实现。注意它 `:33` **只返回温度**。
- `idp/week2_tool.py` —— 本周要写的版本，和 `openai/tool_use.py` 对着读：同一件事的两种写法。

### 四步链路（本周唯一要背下来的东西）
```
给工具清单 → 模型选工具（tool_calls）→ 程序执行 → 结果回传 → 模型组织语言
```

### 知识点
1. 工具声明：`name` / `description` / `parameters`（JSON Schema）——描述写不清，模型就选错。
2. `tool_calls[].function.arguments` 是 JSON 字符串，必须 `json.loads` 再用。
3. 回传格式严格：`assistant`（带 `tool_calls`）→ `tool`（带对应的 `tool_call_id`），顺序不能乱。
4. **工具契约决定模型能说什么**：`weather.py` 只返回温度，模型就答不出湿度和降雨。

### 动手任务
1. 跑 `openai/tool_use.py`，在 `:38` 和 `:50` 各断一次点，看两次请求的 `messages` 有何不同。
2. 写 `idp/week2_tool.py`：从终端读入问题，走完四步链路，打印每一步。
3. 观察并记录：模型把「长沙」翻译成了哪两个数字？它是怎么知道的？（答：靠模型自己的地理知识，
   **不是查出来的**——这正是工具参数不可靠的地方，也是下一步改进的动机。）
4. 新增一个自己的工具（例如「查询某城市当前时间」或「查某支股票的最近收盘价」），
   写好 schema 加进 `TOOLS`，让模型能选中它。

### 验收标准
- [ ] 能不查资料画出四步链路，说清每一步的数据是谁产生的
- [ ] 解释 `tool_call_id` 的作用，以及回传顺序错了会怎样
- [ ] 自己新增的 `TOOLS` 里的工具能被模型正确选中并返回真实结果
- [ ] 能指出本周实现的最大风险（模型自己编造的工具参数）

### 常见坑
| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 第二次调用报 400 | `assistant`/`tool` 消息没按序塞回 | 对照 `openai/tool_use.py:44-49` |
| 模型不调工具 | `description` 太含糊，或问题里没有触发词 | 改 `description` 而不是改模型 |
| `json.loads` 报错 | 直接把参数当 dict 用了 | 先 parse 再展开 |
| 模型硬编经纬度 | 工具参数靠模型内部知识 | 加工具把「地名→经纬度」也查出来（延伸练习） |
| 模型答不出湿度/降雨 | 工具只返回了温度 | 改工具返回值（`openai/weather.py` 只给温度，`idp/common.py` 给温湿度，对比看差别） |

### 延伸练习
- 给工具加一层校验（纬度 -90~90、参数缺字段直接报错）。
- 把 `weather.py` 扩展成返回湿度/降水，观察模型回答能变多丰富。

## 第三周：实现 ReAct 循环，跑通一次思考 → 行动 → 观察 → 最终回答链路

### 目标
把第二周的「一轮定生死」变成循环：模型每轮都可以再要工具，直到它自己觉得信息够了。

### 读这些代码
- `idp/week2_tool.py` —— 上周成果，本周在它之上加循环。
- `openai/llm_architecture.html` —— 结合图文理解「模型输出 → 程序编排 → 再喂回模型」的闭环。

### 知识点
1. ReAct = Reason（思考）+ Act（行动），本质是**一个带终止条件的 while 循环**。
2. 观察（Observation）就是工具结果本身，以 `role: tool` 的消息形式回传。
3. 每一轮的轨迹都要留痕，模型下一轮才知道自己做过什么、做过没有。
4. **必须设最大步数**：`MAX_STEPS` 是防死循环的刹车，不是可选项。

### 动手任务
1. 先在纸上画出状态机：`思考 → (有 tool_calls?) → 行动 → 观察 → 回到思考`。
2. 写 `idp/week3_react.py` 的 `react(messages)`，返回 `(最终回答, 完整轨迹)`。
3. 从终端问「长沙现在天气怎么样？顺便对比一下杭州。」，观察它**转了几轮**、
   每轮调了什么工具、观察值是什么。
4. 故意把 `MAX_STEPS` 改成 1，观察链路被截断时的行为。
5. 想清楚：一次响应里模型可能返回**多个** `tool_calls`，此时每个都要回传一条 `tool` 消息，
   漏一个就会 400。

### 验收标准
- [ ] 能画出状态机并口述每一步
- [ ] 多城市对比类问题能跑通 ≥2 轮，终端能看到「行动/观察」轨迹
- [ ] 能说出 `MAX_STEPS` 设为几、为什么不能无限循环
- [ ] 知道一次响应里有多个 tool_calls 时该怎么回传

### 常见坑
| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 模型反复调同一个工具 | 没有步数上限 / 轨迹没回传 | 加 `MAX_STEPS`，把 assistant 消息留痕 |
| 轨迹越滚越长 | 没做裁剪 | 本周先不管，第四周统一解决 |
| 工具报错整个循环崩掉 | 没有兜底 | 捕获异常，把错误信息当成一条 `tool` 消息回传 |

### 延伸练习
- 加一个新工具（查空气质量 / 查汇率），让 ReAct 能组合两个工具。
- 让循环支持「一次要多个工具」的场景（当前 `week3_react.py` 已按多 tool_calls 处理，可加日志验证）。

## 第四周：给 Agent 加短期记忆，实现多轮会话拼进 prompt

### 目标
让 Agent 记得住上下文——并且让学员明白：**记忆不是免费的，是用 token 和延迟换的。**

### 读这些代码
- `idp/week3_react.py` —— 本周在它之上加一层状态。
- `openai/tokenizer.py` —— 量 token 的工具，第四周后半段要用。

### 知识点
1. 记忆的本质：**把历史重新拼进 `messages`**，靠上下文窗口实现，不是模型侧的能力。
2. 该记什么：`user` / `assistant` **以及工具调用轨迹**。
   只记问答，模型下一轮会重复调同一个工具（自己验证一下）。
3. 记忆有上限：`deque(maxlen=N)` 先进先出，超了丢最旧的。
4. 成本：每轮都把历史重发一遍 → token 线性增长、延迟线性增长。量一量才知道值不值。
5. `system` 提示词建议单独放、不参与滚动淘汰。

### 动手任务
1. 写 `idp/week4_memory.py` 的 `Agent` 类：`history` 存历史，`chat(user_input)` 处理一轮对话。
2. 从终端依次输入：
   - 「我叫杨海波，在杭州做开发。」
   - 「我叫什么？在哪个城市？」
   - 「那边现在天气怎么样？」
   对比第一周同样三句话的效果。
3. 观察第三问：模型**是否重新调了一次天气工具**？不调，说明工具轨迹进了记忆；
   调了，说明轨迹没进历史，去补上。
4. 用 `openai/tokenizer.py` 量一量：聊 5 轮之后，一次请求的 token 涨了多少。
5. 把记忆上限从「消息条数」改成「token 数」，超了就从最早的开始丢。

### 验收标准
- [ ] 多轮对话能正确记住姓名、城市等前文信息
- [ ] 能解释工具轨迹为什么也要进记忆（并有实验佐证）
- [ ] 能说清记忆的代价：token、延迟、以及为什么要设上限
- [ ] 上限逻辑能改成按 token 计

### 常见坑
| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 模型重复调同一个工具 | 轨迹没进 `history` | 把 assistant/tool 消息一起存 |
| `system` 提示词突然失效 | 被滚动淘汰掉了 | `system` 单独放，不参与淘汰 |
| 回答越来越慢、越来越贵 | 历史无限增长 | 设 `max_messages` 或 token 上限 |
| 记忆里全是 `<think>` | MiniMax-M3 把思考过程放进了 `content` | 入库前剥离（进阶） |

### 延伸练习
- 把 `<think>` 剥离逻辑加进 `common.py`，对比剥离前后的 token 消耗。
- 对照 `idp/common.py` 与 `openai/call_llm.py`：两份实现只差在哪？若改成复用 `openai/`
  （包化、或运行时改 `sys.path`），能省多少重复、又要付出什么代价（IDE 解析、交付独立性）？
- 想清楚「短期记忆」的边界：换进程、换会话怎么办？（引出长期记忆/向量检索，不展开。）
